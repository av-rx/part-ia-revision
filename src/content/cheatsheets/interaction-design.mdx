## 1 · Foundations: IxD and user-centred design

### Goals of interaction design

- Develop **interactive** products — UX as well as UI — that are **usable**: help users do something / fulfil tasks.
- Alternatives to UCD: Participatory Design / co-design, Contextual Design, etc.

### Why take a UCD approach

- Useful software sells better. "You aren't your user" — designers rarely match their users.
- A structured way of allowing yourself to be **surprised**.
- Helps **build the right software** (useful purpose) and **build the software right** (usable for that purpose) $\Rightarrow$ a structured way of building **empathy**.

### UCD as part of the software engineering process

- Identify target users/stakeholders; develop requirements.
- Iterative/agile — UCD methods slot into the cycle; people find it hard to say what they want without a concrete artefact to react to.
- **Return on investment:** cost of changes rises roughly **10×** per phase — correcting misunderstandings early saves enormous cost.

### The UCD cycle

1. **Understand context of use** — who, what, where, why.
2. **Specify user requirements** — derived from research.
3. **Produce design solutions** — sketches, wireframes, prototypes.
4. **Evaluate against requirements** — usability test, expert review.

Cycle until requirements are met.

### Types of context for design

| Context | Characteristics | Focus |
|---|---|---|
| **Consumer apps** (discretionary) | User can stop using at any time | "Walk up and use" usability |
| **Enterprise / government apps** (compulsory) | User compelled through work; training possible | Productivity |
| **Socio-technical services** (mixed) | Provision of a service users may/may not take up | No strong a-priori usability priority |

## 2 · User research methods

Research is **empirical** — collects quantitative (numbers) and qualitative (words/images/video) data. Common challenges: recruitment, ethics/risk of distorting data, researcher/participant power disparity, confidentiality/anonymity, incentives.

| Method | Strength | Weakness |
|---|---|---|
| **Unstructured interview** | Rich, interviewee-led data | Too much data, off-target |
| **Semi-structured interview** | Rich AND targeted | Still a lot of data |
| **Structured interview** | Straightforward to collect/compare | Rigid |
| **Focus groups (different stakeholder groups)** | Surfaces tensions between groups | Conflict |
| **Focus groups (same stakeholder group)** | More efficient than individual interviews | Dominant participants / groupthink |
| **Observation — field (ethnography)** | Realistic, authentic behaviour | Hard to set up, intrusive, privacy, Hawthorne effect |
| **Observation — lab** | Less intrusive | Not a realistic setting |
| **Direct + concurrent think-aloud** | Good for understanding context as it happens | Lots of data, time-consuming |
| **Indirect + retrospective protocol** | Good for cognitively demanding tasks | Users forget, time-consuming |
| **Questionnaires** | Reach many people, qual + quant | Rigid, impersonal |
| **Card sorting** | Reveals terminology/relationships/categories | — |
| **Studying documentation** | Available, no stakeholder time needed | Idealised, outdated, insufficient alone |
| **Researching similar products** | Prompts requirements, alternative designs | May inhibit creativity |
| **Analytics / clickstream** | Real, large-scale | Lacks the "why" |
| **Diary studies** | Longitudinal | Requires participant discipline |

**Interview guidelines:** focus on **concrete examples**, ask **open** questions, avoid **leading** questions and jargon.

**Questionnaire question types:** open (free text); closed — numerical, checklist (yes/no/don't know), multi-point rating scale, ranked order.

**Card sorting variants:** **open** (no pre-set groups, participants sort & label freely), **closed** (pre-established groups, participants assign cards), **hybrid** (both).

### Mixed methods designs

| Design | Pattern |
|---|---|
| **Triangulation** | Collect QUAL + QUANT simultaneously, interpret together |
| **Embedded** | One method nested within the other |
| **Explanatory** | QUANT first, then QUAL to explain results |
| **Exploratory** | QUAL first, then QUANT to test/generalise findings |

**Choosing methods** depends on: available time, risk, researcher knowledge, design context, and nature of user tasks (sequential vs overlapping, simple vs complex, layman vs expert).

### Key guidelines for all research

- Focus on users' and stakeholders' needs; involve **all** stakeholder groups (≥1 representative each).
- Get **informed consent**; use **mixed methods**; **plan analysis before collecting data**.
- Iterate on requirements and designs between data-collection activities.

## 3 · Requirements analysis

### What is a requirement

> *"Something that the product must do or a quality that the product must have."* (Robertson & Robertson, 1999)

Answers: what should the software do to meet user needs; what properties/attributes should it have; what constraints apply to development? Without requirements analysis, customers explain needs ambiguously, designers misunderstand wishes, and programmers implement the wrong thing — failures here are **expensive and slow** to fix later.

**Functional** (what the system should do) vs **Non-functional** (constraints: data, environment, user characteristics, usability/UX goals). This split is **imprecise** and falsely implies functional requirements matter more.

### Wiegers & Beatty hierarchy

**Business Requirements** → Vision & Scope Document → **User Requirements** → User Requirements Document → **Functional Requirements** → Software Requirements Specification.

**Business Rules** influence all levels; **Quality Attributes**, **External Interfaces**, and **Constraints** feed into the SRS.

| Type | Definition |
|---|---|
| **Business Requirement** | High-level objectives of the org/customer — *why* are we building this? |
| **Business Rule** | Policy/guideline/standard/regulation constraining the business — origin of requirements, not itself a software requirement |
| **User/Stakeholder Requirement** | Goal or task users must perform — captured via use cases, scenarios, user stories |
| **Quality Requirement** | Non-functional — *how well* the system performs: usability, performance, reliability, maintainability, security, portability, interoperability |
| **Functional Requirement** | A behaviour exhibited under specific conditions — inputs, outputs, functionality, data manipulated (a.k.a. *solution requirement*) |
| **System Requirement** | Top-level requirement for a multi-system product |
| **External Interface Requirement** | A connection to the outside world — user, other system, or hardware |
| **Constraint** | Restriction on developer choices — implementation/delivery, technology, dev environment, legacy systems, existing DBs |

**Mapping to dev process:** *What to build, for whom, why?* → Business Requirements. *What features matter most?* → User/Stakeholder Requirements. *How should each feature work?* → Functional Requirements. *Is it usable?* → Quality Requirements.

**Worked example (hiking app):** User Requirement — maintain accurate UK hiking map, plan/track hikes via GPS, warn if off-course. This decomposes into Functional Requirements (offline map with terrain/weather overlays, weekly update checks), Constraints (Android & iOS), Reliability (offline tracking), Usability (onboarding < 10 steps). Design/prototyping bridges **User → Functional Requirements**; implementation realises the **SRS**.

## 4 · Exploring the design space

### One requirement, many designs

The same user requirements can be implemented many ways (e.g. Audible, Google Books, LibriVox all differ in layout for the same audiobook task). Constraints and quality attributes prune the space, but infinite possibilities remain.

### UCD approach to design

Create and compare alternative designs while (1) **keeping the user in mind** — improve their environment and goals, not just system requirements, and (2) **being iterative**: $\text{design} \to \text{measure/test} \to \text{redesign}$.

Methods overview: brainstorming, moodboarding, concept development, design principles, storyboards, prototyping — mix and match as the project demands.

### Brainstorming

Generates ideas to solve design problems; one facilitator. House rules: time limit, start from a target problem/brief, no judgment/criticism, encourage wacky ideas, aim for **quantity**, build on others' ideas.

**Structuring team interaction:** **Group** (individuals contribute directly, e.g. Osborn's method); **Individual → Group** (brainstorm alone then share — nominal group technique, team idea mapping); **Individual ↔ Individual → Group** (respond to others then discuss as a group — group passing, directed brainstorming).

**Structuring idea generation:** brain-netting (no structure), mind mapping (associations), starbursting (what/where/when/why/how per idea), gap analysis, SWOT analysis.

**Challenges:** peer pressure, groupthink, disengagement, dominant voices. Mitigations: anonymous idea collection, clear facilitator role, time-boxing, individual-first techniques.

### Moodboard

A **collage** giving the "feel" of a design (images, text, samples) — used to develop concepts/style guides and communicate to the team. Feeds into (but is distinct from) the **style guide** (typography, colour, components) → final UI. Different personas drive radically different moodboards (commuter → calm/escapist; teen skater → bold colours; retiree → cozy/literary).

**Challenges:** must match branding while supporting usability; easy for visuals, harder for interaction; little tool support; subjective and hard to critique.

### Concept development

Identifies a **driving concept or metaphor** that drives both **graphic** decisions (layout, colours, fonts, imagery) and **interaction** decisions (UI elements, widgets, animation, navigation). A strong concept produces a **coherent** design.

- **Verbal concepts** — words describing the interface; abstract; focus on the *message*.
- **Visual concepts** — images/colour schemes; concrete; focus on *how* the message is conveyed.

Brainstorming and moodboarding both feed concept creation. Examples: Apple's **desktop metaphor** (folders, files, trash); Microsoft OneNote's **notebook metaphor** (coloured-tab sections, pages, drawing as input).

**Challenges:** match branding while supporting UX; literal implementation can distract; getting team agreement on a common vision.

### Product-specific design principles

Value statements that frame design decisions — distinct from generic universal/platform principles. Used to focus design around user values, build a **consistent** experience, get **team alignment**, fuel creativity, speed decisions.

**Examples:** **Medium** (Dustin Senos) — *Direction over Choice* (limit layout/type/colour choices to keep focus on writing), *Appropriate over Consistent* (break consistency when context warrants), *Evolving over Finalized* (drafts/notes improve with use). **Firefox Design Values** — Takes care of you, Plays well with others, Exuberance, Finely crafted, Global, Balances power and simplicity, Makes sense of the web, High user-performance, You help make it.

**Where values are used (Firefox model):** (1) filter which design opportunities to pursue, (2) shape decisions during refine & test, (3) guide implementation trade-offs/what ships, (4) establish what success looks like.

**Good principles are:** small in number (3–5, memorable); differentiating (explain why a user picks *you*, not generic truisms); unambiguous and actionable; concise.

**Challenges:** too generic/not opinionated; can interfere if too rigid; prioritising which matter most.

### Storyboards

A rough **series of frames/drawings** showing a sequential storyline of how a user progresses through activities — forces thinking about user flow/tasks, iterates quickly, communicates what users (can) do and how.

**Two foci:** **context around interaction** (user in environment with thoughts/emotions) vs **screen & interaction flow** (wireframes connected by transitions/annotations).

**How to create:** (1) persona + scenario, (2) sequence of actions, (3) add solution detail, (4) write the story, (5) draw, (6) caption each frame.

**Challenges:** wrong level of detail (must show interaction, not just screens); cost (good storyboards take time/revision); version management as features change.

### Prototyping — overview

> An incomplete, early version of a product — interactive but not production-grade. The best way to evaluate alternative designs is letting users interact with them (see Wizard of Oz, §9).

**Why prototype:** **sketch** (explore design space — interaction, form, tech, concepts, content); **demo** (to team/client/user/funder); **develop design** (test concepts/assumptions, "thinking through making", choose between alternatives); **evaluation/user testing** (objective feedback, real usage, find problems & opportunities).

**What to prototype:** technical aspects, workflow/task design, screen layouts, look-and-feel, content/taxonomy, controversial/critical areas (security, privacy).

**Kinds — by polish:** low fidelity (lo-fi) vs high fidelity (hi-fi). **By interactivity:** non-interactive (storyboards, wireframes) vs interactive (click-through — Adobe XD, Balsamiq, PowerPoint — or coded).

| Kind | Characteristics | Used for |
|---|---|---|
| **Paper** | Drawing/diagram/photoshop; quick, cheap, sketchy; many iterations | Early exploration, lo-fi user testing |
| **Wireframe** | Schematic of IA; layout only, no visual design | Structuring screens before visual design |
| **Video** | Quick or complex; sketchy or polished; tells a story | Demo impossible/costly — speculative tech, future scenarios |
| **Form model** | Doesn't work but shows form; rough or refined | Shows object in the world; allows direct handling (e.g. Palm Pilot wooden block) |

## 5 · Prototyping fidelity in depth

### Fidelity continuum

| Fidelity | Examples | Cost | Best for |
|---|---|---|---|
| Sketches | pencil, whiteboard | minutes | brainstorming, divergence |
| Paper prototypes | hand-drawn screens, cut-outs | hours | early flow & nav |
| Wireframes | Balsamiq, Figma greyscale | hours | structure, information architecture |
| Interactive wireframes | Figma click-through | day | flow + light interaction |
| Hi-fi mockups | Figma full-colour | days | visual design, brand |
| Hi-fi clickable | Figma + Smart Animate | days | usability tests, stakeholder demos |
| Coded prototype | minimal app/site | weeks | technical feasibility, performance |

### Low fidelity prototyping

Rough hand-drawn sketches (pencil & paper, post-its). Goal: **quick, cheap, easy to change**; detail key elements + how users interact. Used for multiple alternatives, testing with users (Wizard of Oz), feedback on **interaction & concepts** rather than visuals.

- Cheap to throw away — encourages exploring many ideas; critique focuses on structure, not aesthetics; anyone can contribute.
- Less convincing for stakeholders; limited evaluation of detailed interaction (animation, latency, exact wording).

### High fidelity prototyping

Interactive, often implemented (code or Adobe XD-like tools). Goal: realistic visuals & interaction for evaluation/refinement; mix of real and simulated content. Used for usability/flow testing and to support investment/sales.

- Realistic feel — better testing of visual/micro-interactions, stakeholder buy-in, ready to hand to developers.
- Expensive to change — **anchoring effect** (people commit to embodied ideas); risk users think it's real (unsafe to enter real data).

**Rule of thumb:** match fidelity to the *question you're testing* — nav layout → wireframes suffice; complex animated transition → go hi-fi.

### Throw-away vs evolutionary

- **Throw-away:** prototype is a learning artefact, not future code — avoids "code rot".
- **Evolutionary:** prototype evolves into the production system — faster, but risks accumulating shortcuts.

The Cambridge syllabus emphasises **throw-away** prototyping early — separating "exploring the design space" from "engineering the system".

### Wizard of Oz

A human secretly drives behaviour the system would later automate — particularly useful for prototyping ML/AI features before the model exists. Tests the UX of the *experience*, not the underlying tech.

### Why prototype (cost framing)

Prototyping is **cheap thinking aloud in a tangible artefact**. Design-change cost grows roughly **10×** per subsequent phase (requirements → design → implementation → test → production) — prototyping lets you explore and iterate before investment locks you in.

## 6 · Cognitive aspects for design

Three considerations for HCI design: **perception & cognition** (memory, visual perception, attention), **interaction** (affordances, form factor, input modalities, gestures), **content understanding** (information architecture, data modelling). Practical tools that generalise these: interaction design patterns, UI toolkits, design systems (§7).

### Memory — Atkinson–Shiffrin model (1968)

Three stores connected by cognitive processes; **rehearsal** loops within short-term memory; **retrieval** pulls from long-term back to short-term.

**Short-term memory (STM):** holds (doesn't manipulate) a small amount of info, active and readily available, for a short time.
- **Duration** ≈ 15–30s, extendable by rehearsal.
- **Capacity** ≈ 7 items, varies by type (≈7 digits, ≈6 letters, ≈5 words) — Miller (1956), *"The Magical Number Seven, Plus or Minus Two"*.
- **Chunking** extends capacity by grouping items, e.g. `7562986224741` vs `756 298 622 741`.
- *Design implication:* tooltips reduce STM load by showing relevant data on hover instead of forcing recall across screens.

**Long-term memory (LTM):** **explicit/declarative** — episodic (events, e.g. entering the building this morning) and semantic (facts, e.g. capital of a country); **implicit/procedural** — motor skills (tying shoelaces, riding a bike). Memorisation is usually by repetition, or when something is surprising; we learn by **association**.

- *Design implication:* established conventions (login/basket top-right, nav tabs along top, filters on left sidebar) reduce learning cost by letting users transfer existing memory — same with code, where similar syntax across languages lets a learner transfer a known mental model.

**Activation of content in memory** increases with **practice**, **recency**, and **context** (what else is in focus of attention).

**Recollection vs recognition (Yonelinas, 2002):**

| Property | Recognition | Recollection |
|---|---|---|
| Speed | Faster | Slower |
| Sensitive to divided attention? | Less | More |
| Dependence | Independent of recollection | — |

*Design implication — recognition over recall:* **labelling** (icons + text, e.g. Android clock app labels ALARM/CLOCK/TIMER/STOPWATCH); **reusing visual patterns** (heart icon for "love it"); **code completion** in IDEs (recognise rather than recall API names).

### Visual perception — Gestalt principles

The whole is perceived as more than the sum of its parts. Seven principles:

1. **Similarity** — *make equal elements look equal.* Group similar elements (shape, size, colour) into one unit (Google search result rows; BBC headline/date/section styling). **Anomaly** (breaking similarity) draws attention — used to show selection.
2. **Proximity** — *group related things.* Elements close in space are perceived as one unit (Amazon footer link groups, Craigslist category columns).
3. **Enclosure** — *border related things.* Elements enclosed by a visual border belong together — lines, background colours, separators (BBC story dividers, eBay product cards).
4. **Common fate** — *move related things together.* Elements moving together belong together (Amazon expanding menus, Netflix carousels sliding as a unit).
5. **Figure/ground** — *make content stand out from background.* Separate foreground (figure) from background (ground) — modal overlays, dimmed backgrounds, hero images with CTAs. **Figure-ground ambiguity** (Rubin's vase) exploited in poster design.
6. **Closure** — *viewers fill in visual gaps.* Icons from disconnected strokes still read as coffee cup, pin, printer, wifi. ⚠ **Bias warning** — if the missing part isn't a simple shape, closure misleads (e.g. a gap in a line chart is interpolated smoothly even if real data was jagged).
7. **Good continuation** — lines/curves perceived as continuous even where they intersect other objects. Crossing lines in multi-series charts are still tracked as continuous (helped by colour); decorative connecting paths guide the eye through a story.

### Attention

> *Selectively concentrating on a discrete aspect of information whilst ignoring other perceivable information.* Multi-modal (visual, auditory, verbal, tactile); incomplete, inaccurate, limited.

**Types (Spotlight Model):** **reflexive/exogenous** (external cues) vs **intentional/endogenous** (internal cues). Small **focus**, surrounded by blurry **fringe**, beyond which is the **margin**.

**Reflexive vs intentional (Jonides, 1981):** external cues get more processing time and accuracy, are harder to ignore, remain effective under cognitive load, and draw attention even when unexpected.

*Design implication — control visual noise:* cluttered sites/editors overwhelm the visual system and hide important detail (e.g. a missing brace). Good choices: **notifications** (surface what matters, when it matters); **progressive disclosure** (reveal options as needed, e.g. Duolingo's placement test → drills).

### Affordances

> Visual design that suggests and encourages the right interaction.

- A door handle's shape suggests wrapping a hand around it and rotating.
- A raised rectangle with a label suggests it can be **pressed** (button).
- A row of items cut off at the edge suggests **scrolling**.
- Underlined/coloured/arrow-marked text suggests **clicking**/linking.

⚠ Affordances make UIs **easy to learn** — not innate; users rely on prior experience of conventions.

### Physical form of user interfaces

UI types: **physical** (consumer electronics), **screen-based** (mobile/laptop/desktop — course focus), **wearables**, **speech**, **VR**, **tangible**, **robot**. Screen-based interfaces have two components: **presentation device** (screen/monitors) and **input device(s)** (touchscreen, touchpad, mouse, keyboard).

**Constraints on design:**
- **Form factor** — hardware dimensions: size (phone/tablet/laptop/multi-monitor), screen ratio (portrait/landscape, fixed/rotatable). E.g. the same web app uses a single-column hamburger layout on phone vs multi-column persistent nav on desktop.
- **Input modality** — input points (single/multi-touch), available gestures (point, click, scroll, hover, swipe, pinch). E.g. pinch-to-zoom on phone maps vs ⌘+scroll on desktop.
- **Combined example:** video editing on laptop (Premiere Pro, mouse+keyboard, multi-panel) vs phone (CapCut, touch gestures, simplified timeline) — same task, fundamentally different IxD.

## 7 · Content, information architecture, and design tools

### Information architecture (IA)

> The practice of deciding how to arrange the parts of something to be understandable.

**Aims:** organise content/functionality into **taxonomies and hierarchies**; define **relationships**; **tag** content with metadata; design **search** strategies.

**Process:** (1) **Inventory** — what content exists/is needed; (2) **Establish a taxonomy** — high-level structure; (3) **Chunk** — divide into logical units; (4) **Diagram** — structure & navigation; (5) **Analyse** — test with real users and revise. Applies across abstract/detail levels — whole system → page → section.

### Taxonomy types

| Type | Relationship | Example |
|---|---|---|
| **Flat** | Enumeration | List of items |
| **Hierarchy** | *is-a* (content ↔ category) | Sitemap tree |
| **Faceted** | *has-a* (content ↔ attributes) | Filterable product catalog |
| **Network** | Association (e.g. multiple tags) | Tag clouds |

Surfaced via **navigation** and **sitemaps**; **card-sorting** elicits taxonomies from users' own perspective.

### IA diagramming best practices

- Focus on **structure**, not hierarchy — hierarchy can change, structure should not.
- **Processes should be logical** — links should help users achieve tasks.
- IA is part of **UCD** — based on user research; consider the **users of the IA itself** (PM, dev team); must **change over time** as the system evolves.

### Page-level IA & navigation

- **Match user expectations** for content location — only move things with rationale; **consistency** and cognitive aspects help; **wireframes** map page structure.
- **Common mobile app structures:** Hierarchy/Catalog (drill-down list, e.g. Sainsbury's), Hub & Spoke (central hub + detail pages, e.g. Google Maps place), Nested Doll/Flow (linear sequence, e.g. booking flow), Tabbed View (peer screens via tabs, e.g. Clock app), Dashboard (summary, e.g. Fitbit), Filtered View (e.g. Play Store top charts).
- **Navigation directions:** lateral (same hierarchy level), forward (top→down), reverse (back, chronological/hierarchical). **Search** is an alternative for locating content quickly — IA must be complemented with UCD (requirements + testing).

### Data modelling

Frontend (UI) and backend (data structures/algorithms) both need design decisions. IA organises information *for the user*; data modelling asks how/for-what the data will be used, trading off system performance and end-to-end user requirements.

- **Example — tagging:** how tags are used drives the model (add/remove on messages & conversations, grouped, some emphasised) → **no hierarchy**: flat tag objects with metadata (`groups`, `filterable`, `type`, `visible`); messages reference tags by **id**, not embed.
- **Example — messaging:** Option A — server stores `User —1:n— Conversation —1:n— Message` explicitly; Option B — server stores only `Message` (from, to, text, date, status) and the client reconstructs conversations/users. The backend needn't model abstractions the client can derive.

**Principles:** design with the user in mind; keep structures flexible (systems evolve); balance backend/frontend needs (UI reshaping can introduce bugs); align system properties with user requirements; don't choose technical elegance over usability.

### Practical tools: patterns, toolkits, design systems

Three overlapping tools — **interaction design patterns**, **UI toolkits**, **design systems** — provide solutions/implementations of common IxD problems at increasing levels of integration.

**Interaction design patterns** — origin: Christopher Alexander's *A Pattern Language* (architecture) → GoF *Design Patterns* (software) → Tidwell's *Designing Interfaces* (UI). Useful as a learning tool, quick solutions, ensuring **consistency**/matching **user expectations**, and offering a **vocabulary** for discussion. A pattern has five components: title, problem, context, solution, example.

| Pattern | Problem | Context | Solution |
|---|---|---|---|
| **Navigation Tabs** | Navigate site/app sections with clear current-location indication | 2–10 sections; short, predictable, stable titles; top-level nav | Single-line horizontal row of tabs (usually top); whole tab clickable; maintained across pages |
| **Breadcrumbs** | Navigate up/back in hierarchy, understand location | Page within a hierarchy; no other local nav exposes it; user may arrive via search | Single-line list of labels from topmost page to current |
| **Carousel** | Browse visually-similar items, possibly select one | Items represent well visually; limited space; 3–8 shown at a time | Horizontal row of thumbnails with nav arrows or scroll/swipe |

**UI toolkits** — a collection of UI components/widgets with common theming, for easy access + consistency. **Bootstrap** (CSS classes, pre-built components, configuration options); **Untitled UI** (Figma kit + design system, variants, customisable styling, example pages).

**Design systems** — *interaction design patterns + UI kits + strict rules of usage*: reusable components guided by clear standards. Advantages: faster development, shared rationale, unified cross-team language, cohesive UX, easier maintenance/scalability. **Example — Google Material Design** (Android/iOS/Flutter/web): guided by principles (*Material is the metaphor*, *Bold, graphic, intentional*, *Motion provides meaning*); components have built-in states (focus, selection, hover, press, drag, disabled); supports **theming** (colour/typography/shape per brand); per-component docs cover usage, anatomy, behaviour, placement, states, specs.

**Limitations (all three):** a catalogue is **not a checklist** — pick the right pattern/component for context; some patterns solve the same problem differently; appearance and interactivity (screen size, touch vs click) are still left to decide; **not a replacement for UCD** — verify user needs first.

## 8 · User research data analysis

Data must be analysed to relate findings to users, keep users in mind during design decisions, and discuss implications with the team. Different data types need different analysis approaches.

**Quantitative** (numbers — size, magnitude, statistical significance) vs **qualitative** (words/pictures/video — themes, patterns, stories; can be counted but loses depth).

| Method | Qualitative example | Quantitative example |
|---|---|---|
| Interviews / Focus groups | Audio/video, interviewer notes, open responses | Demographics, closed questions |
| Observation | Observer notes, photos, think-aloud | Demographics, time on task, # people |
| Questionnaires | Open + "further comments" | Demographics, closed responses |
| Card sorting | Records of behaviour & comments | Categories, items per category |

### Quantitative analysis

- **Central tendency:** mean, median, mode. **Variability:** range, standard deviation $\sigma$, variance ($\sigma^2$). **Categorical distribution:** percentages.
- **Graphical representations:** bar, pie, scatter, time series, histogram, maps. ⚠ Don't mislead with numbers.
- **Anscombe's Quartet:** four datasets with **identical** summary statistics but very different shapes when plotted $\Rightarrow$ always **visualise** data.
- **Card sorting analysis:** build a pairwise **similarity (co-occurrence) matrix**; **hierarchical clustering/dendrogram** visualises groupings at each dissimilarity level — reveals participants' mental categories (e.g. tomatoes grouped with vegetables despite being botanically a fruit).
- **Tools:** spreadsheets; SPSS/STATA; RAWGraphs/Tableau/Power BI; UXtweak/OptimalSort for card-sorting.

### Qualitative analysis

**Basic approaches:** critical incidents (key events), identifying themes (emergent/**inductive**), categorising data (pre-specified scheme/**deductive**) — combine all three in practice.

**Analytical frameworks:**

| Framework | Data | Focus | Expected outcomes | Granularity |
|---|---|---|---|---|
| **Conversation analysis** | Recordings of spoken conversation | How conversations are conducted | Insights into how conversations are managed | Word-level, pauses, inflection |
| **Discourse analysis** | Recordings of speech/writing | How words convey meaning | Implicit/hidden meaning in texts | Word, phrase, sentence |
| **Content analysis** | Any "text" (written, A/V, photos) | Frequency of items in text | Frequency of items appearing | Words → feelings → artefacts |
| **Interaction analysis** | Video of natural activity | Verbal/non-verbal interaction with artefacts | Insights about knowledge/action use | Artefact, dialogue, gesture |
| **Grounded theory** | Empirical data of any kind | Building a theory around the phenomenon | Theory grounded in empirical data | Varies |
| **Systems-based** | Large-scale, heterogeneous | Large orgs (hospital, airport) | Insights about organisational effectiveness | Macro/organisational |

**Thematic Analysis (TA):** codes (small labels for data fragments) → grouped into **themes** → optional **sub-codes**. Themes are emergent groupings of related codes (e.g. *Robot capabilities* covering *engagement*, *empathy*, *feedback*, *instruction*). Output paired with **representative quotes**.

**Tools:** paper & markers, spreadsheets; NVivo, Atlas.ti, CAQDAS Networking Project, Coda.

### Presenting findings

Depends on **audience**, **purpose**, and **methods used**. Present an **evidence chain** showing how findings derive from underlying data (adds richness, guards against over-interpretation). Quant + qual often combined (e.g. scores alongside participant quotes).

## 9 · Keeping the user in mind: stakeholders, personas, scenarios, journey maps

Tools to summarise findings concretely and guide design: stakeholder analysis, personas, scenarios, journey maps.

### Stakeholder analysis

Identifies stakeholders, tracks their interests, prioritises product development.

- **Target users** — primary stakeholder(s); can span more than one group (e.g. CamCORS: students, supervisors, DoSes).
- **Other stakeholders** — those who **influence** (e.g. parents managing a child's device), are **affected** (e.g. friends of a runner using a trail map), or **support** the interaction (e.g. helpdesk staff).

**Types — from the product (Eason, 1987):** **primary** (frequent, hands-on), **secondary** (produce input/receive output, don't directly use it), **tertiary** (affected by introduction or influence purchase), **facilitating** (design/dev/maintenance).

**Types — from the organisation:** **internal** (employees, managers, owners), **external** (customers/users, community/society, suppliers, shareholders, government).

**Stakeholder mapping (2×2 grid — Priority × Involvement):**

| | Low involvement | High involvement |
|---|---|---|
| **High priority** | Address their concerns | Involve them extensively |
| **Low priority** | Keep them informed | Involve them as needed |

**Challenges:** finding the right people; balancing different needs/priorities; engaging stakeholders at the right time.

### Personas

User archetypes constructed from research data — **fictitious, specific, concrete** representations of target users (e.g. "Betty"). Puts a face on the target user group ("would this work for Betty?") and helps make user-aligned trade-offs ("works for Betty but not Jake — try this instead").

**Types:** **Focal** (primary users, design optimised for them, ≥1 required ≤3 recommended), **Secondary** (also use the product, satisfy when possible), **Unimportant** (low-priority misusers), **Affected** (don't use it but affected, e.g. spouse of a travel-site user), **Exclusionary** (explicitly *not* designed for — stops non-users creeping into discussions).

**Creating a persona:** (1) review research on the stakeholder group, (2) identify common attributes, (3) identify differences from other groups, (4) describe a unified persona — can be a **collage** of multiple users; the goal is empathy, not realism.

**What to include:** name, photo, demographics; personality (a quote/slogan); product-specific goals/needs/attitudes/motivations (not tasks), knowledge/proficiency, frustrations, context of usage.

**Challenges:** superficial/stereotypical; "what you see is all there is" bias; cost of producing well-grounded personas. Mitigation: ground in real data, validate with users, update as understanding evolves.

### Scenarios

> *"A concise description of a persona using a product to achieve a goal."* (Cooper, 2004)

**Concise** (short but complete, breadth over depth), **product** assumed to exist, **goal**-driven.

**Why use them:** validate design and check assumptions; bridge theoretical/conceptual design to lo-fi/wireframe; create shared understanding of users across designers, marketers, engineers, execs. Developed in brainstorming/scenario-mapping workshops — answer *what* the user wants, *why*, *how* they'll achieve it, *what they're thinking*.

**Types:** **Goal/task-based** (goal + reason only, no *how* — design/usability testing); **Elaborated** (adds context/user details — design stage); **Full-scale task** (includes the steps — validates against real usage in dev/testing).

**Challenges:** too superficial; wrong level of detail; **linearity** (limited handling of unforeseen events).

### Journey maps

Visualisation of the process a person goes through to achieve a goal. Built up: persona + scenario + goals/actions ⟹ **timeline**; + thoughts/emotions ⟹ **narrative**; + opportunities/pain points ⟹ **journey map**. Useful for verifying the user's story makes sense and discussing product fit with stakeholders.

**Typical structure:** **phases** (e.g. Awareness → Adoption → Engagement → Retention → Contribution); **activities** per phase; **emotions** (with representative quotes); **pain points**; optional opportunities/ownership/metrics.

**Challenges:** superficial if not based on real research; linearity; "what you see is all there is" bias; cost.

> ⚠ **Always remember:** people are diverse — don't assume all users use the product the same way. Different devices, interaction techniques, assistive tech, and adaptive strategies bring different experiences and expectations.

## 10 · Evaluation without users: heuristic evaluation

### Why evaluate?

- **Compare multiple designs** against user requirements; feed into a better one.
- **Verify** the solution meets requirements; if not, evaluation suggests fixes; improve design as part of **iterative development**.

**Two categories** (course focuses on practical/quick methods = **"discount usability"**): **without users** (Heuristic Evaluation, Cognitive Walkthrough) vs **with users** (Usability Testing, Controlled Experiments).

### What heuristic evaluation is

> A method using a fixed set of good-practice **heuristics** to find common usability problems.

A **discount usability** technique — cheap, fast, no real users needed; can evaluate sketches, prototypes, or production systems. **3–5 evaluators** each check independently against the heuristics; compiled problems inform redesign.

**Process:** (1) pre-evaluation training (heuristics & scenarios); (2) evaluate individually, go through **twice** (overview then detail); (3) collate results; (4) rate severity individually then discuss/agree; (5) feed into design.

### Severity ratings (Nielsen scale)

A combination of **frequency**, **persistence**, and **impact**.

| Score | Meaning |
|---|---|
| 0 | Not a usability problem |
| 1 | Cosmetic — fix if time permits |
| 2 | Minor — low priority |
| 3 | Major — important to fix |
| 4 | Catastrophe — imperative to fix |

### Nielsen's 10 heuristics in detail

1. **Visibility of system status** — keep users informed via appropriate, timely feedback. UI response thresholds: **\<200 ms** no indicators needed; **1 s** user notices delay; **10 s** max for user to stay focused on one action $\Rightarrow$ use progress bars/indicators.
2. **Match between system and the real world** — speak the user's language: familiar words/phrases/concepts, not internal jargon.
3. **User control and freedom** — users perform actions by mistake; need a clearly marked "emergency exit". **Total exit** → "home" button; **soft exit** → "back"/Esc.
4. **Consistency and standards** — different words/situations/actions shouldn't mean the same thing; follow platform conventions (e.g. burger menu top-left, search top-right).
5. **Error prevention** — good error messages matter, but the best designs **prevent problems** outright (autocomplete, caps-lock warning).
6. **Recognition rather than recall** — make elements/actions/options **visible**; minimise memory load (menus, breadcrumbs, labelled icons).
7. **Flexibility and efficiency of use** — shortcuts (hidden from novices) speed up expert use; let users tailor frequent actions.
8. **Aesthetic and minimalist design** — no irrelevant information; every extra unit competes with relevant ones.
9. **Help users recognise, diagnose, and recover from errors** — plain language (no error codes), precisely indicate the problem, suggest a constructive solution.
10. **Help and documentation** — best if no explanation is needed, but docs may still help. **Proactive help** (templates offered upfront) vs **reactive help** (help menu always available).

### Analysis: cost-effectiveness

- **Discount method** — benefit-cost ratio of **48** (Nielsen, 1994), e.g. \$10,500 cost for \$500,000 benefit. **1 evaluator** finds **~35%** of problems; **5 evaluators** find **~75%**; **diminishing returns** beyond — benefit/cost peaks at **4–5 evaluators**.
- **Pros:** cheap & quick; easy to learn; finds many problems. **Cons:** not task-focused; no real users; not rigorous; can be too generic for new products.

### Derivations

Nielsen's 10 is one set — designers may make their own, e.g. **Andy Budd's *Heuristics for Modern Web Application Development*** (2007): user expectations, clarity, minimising complexity/cognitive load, efficiency, context, consistency/standards, error prevention, error recovery, enjoyable UX.

### Heuristic eval vs user testing

| Aspect | Heuristic eval | User testing |
|---|---|---|
| Cost | Low | Medium–high |
| Speed | Days | Weeks |
| Real users | No | Yes |
| Catches catastrophes | Yes | Yes |
| Catches subtle real-world issues | Poor | Good |
| Captures emotion/context | No | Yes |
| Captures cognitive load | Weak | Good |

**Use both** — heuristic eval first to clean up obvious violations, then user testing to uncover what experts miss.

## 11 · Cognitive walkthrough

> A **task-centred** evaluation by experts to find usability problems for **first-time users**.

Originates from **CE+ theory** (Polson, Lewis, 1990) — models the user as someone who tries actions and learns from feedback. Focuses on real, complete, representative tasks; evaluates problems first-time users hit without training; imagines behaviour of **entire classes of users** (cf. personas), not one. Most effective when evaluators can picture the real environment of use.

**Useful for finding:** assumptions about user thinking; missing/hard-to-find controls; inadequate feedback; difficulties with labels/prompts.

### Process

1. **Define inputs:** **users** (target group + knowledge of similar systems); **sample tasks** (representative, goal-oriented — "send a £20 transfer to a friend", not "explore the app"); **action sequences** (correct steps, granularity depending on task/user expertise); **interface description** (storyboard, prototype, or product).
2. **Get the analysts** — usually usability experts (not users, unlike HE); team members can participate but must "unlearn" the design.
3. **Walk through action sequences** — tell a **credible story** for each action, asking the four questions below.
4. **Record:** user knowledge requirements; assumptions about user population; side issues & design changes; the success/failure story.
5. **Revise the interface:** user fails to select right action → eliminate it, prompt user, or signal availability; doesn't know it's available → make more obvious; doesn't know which action is correct → label based on user knowledge, check sequence makes sense; can't tell things are going OK → give feedback. Many problems are system-user mental-model mismatches → **global** solutions, not local fixes.

### The four questions (per step)

1. **Will the user try to achieve the right effect?** — do they have the *intent* this step expects?
2. **Will the user notice that the correct action is available?** — is the control visible and identifiable?
3. **Will the user associate the correct action with the effect they want?** — does the label/icon match their mental model?
4. **If the correct action is performed, will the user see that progress is being made toward the goal?** — is the feedback clear?

A "no" to any question = a usability defect — record the step, which question failed, why, and severity/suggested fix.

**Success vs failure stories:** **credible success story** — all success criteria met; **failure story** — at least one criterion not met.

### Analysis

**Strengths:** finds **severe problems** fairly well; finds **specific** rather than general problems; strong on **learnability** (first-time users).

**Limitations:** cannot evaluate every task; users may take different action sequences; each task evaluated **separately** — cross-task interactions are missed. Pair with a task-free user-centred method (e.g. HE).

### When to use

- **Before** the system is fielded; **onboarding-critical** systems (kiosks, ATMs, public services where users get one shot); no access to real users; cheaper than user testing for *learnability*.

### Streamlined cognitive walkthrough (Spencer, 2000)

Drop questions 1 and 4 in early walkthroughs (too speculative); focus on 2 and 3 — visibility and labelling, the most common UI failures. Run as a group with explicit "ground rules" (no design defence, no premature solutions).

### Cognitive walkthrough vs heuristic evaluation

| Aspect | CW | Heuristic eval |
|---|---|---|
| Focus | Learnability for *new* users | Broad usability |
| Granularity | Per-step, per-task | Per-screen, per-element |
| Output | Step-level defect list | Violation list with severity |
| Best for | Onboarding, infrequent-use systems | Mature UI polish |
| Skill required | Task analysis + cognitive theory | Usability heuristics |

Many practitioners run both — CW first to validate task flow, then heuristic eval to polish details.

### Derivations

Applies to **APIs** — evaluates whether participants can build an accurate mental model of the API from code alone (O'Callaghan, 2010, *The API Walkthrough Method*).

## 12 · Evaluation with users: usability testing and controlled experiments

| Type | Data | Cost | When |
|---|---|---|---|
| **Usability testing** | Qualitative (behaviour, speech) | Cheaper | Find problems, feed into design |
| **Controlled experiments** | Quantitative (speed, accuracy, error rate) | More expensive | Compare 2+ designs when metrics matter |

### What usability testing is

> Testing a product with representative users to collect feedback for improving the design.

ISO 9241-11 defines usability as the **effectiveness, efficiency, and satisfaction** with which specified users achieve specified goals in a specified context of use.

**Uses:** gain info from the user's perspective (usable? which features work? what problems?); find out satisfaction (would they use it? what can improve?); make **design recommendations**; establish **benchmarks**.

**Formative** (during development — find problems to fix, iterative) vs **Summative** (after development/benchmarking — measure how good it is, larger samples, statistical comparisons).

### Designing the study (8 steps)

1. **Decide objectives** — clear, testable; motivates tasks, data collection, interview questions.
2. **Participants** — match the target user; define inclusion criteria.
3. **Prepare task instructions** — realistic, scenario-based, non-leading ("find the cheapest flight from London to Tokyo on the 10th", not "click the search button").
4. **Find a location/environment** — lab vs remote vs field; control vs ecological validity.
5. **Pilot** — 1–2 trial sessions; refine tasks/protocol.
6. **Recruit** — Nielsen rule of thumb: 5 users find ~85% of issues *in one iteration*, but multiple iterations and diverse subgroups need more.
7. **Conduct test** — greeting & intro → informed consent → background questionnaire (optional) → task instructions → task performance & recording (facilitator + observer + screen/audio/face recording) → debrief.
8. **Analyse and report findings** — code observations, identify patterns, rate severity.

### Ethical considerations

An ethical test has: **minimal risk**; **informed consent**; **minimise deception**; participant may **withdraw at any time**; data kept **confidential**; participant may **withdraw their data**.

**Informed consent must state:** purpose of study; what the participant will do; right to withdraw without reason; how results are used and kept confidential; right to have results excluded.

Other considerations: **anonymisation** of recordings; usability sessions can feel like exams — reassure participants ("we're testing the system, not you"); fair **compensation** for time/travel.

### Think-aloud protocol

Participants speak whatever comes to mind as they do tasks (e.g. *"I'm looking for a button to save… maybe under 'File'?"*) — reveals their mental model, identifies the **locus of attention**, spots frustration/confusion.

- **Concurrent** — speak as they go; risk of interfering with task performance (cognitively demanding tasks may cause participants to stop talking).
- **Retrospective** — replay video, narrate after the fact; captures performance better but relies on recall.

### Common metrics

- **Success rate** — % of users completing the task.
- **Time on task** — median preferred (mean sensitive to outliers).
- **Errors** — count per task, severity-weighted.
- **Efficiency** — pathway length vs optimal.
- **Subjective** — Likert satisfaction; preference between alternatives.
- **System Usability Scale (SUS)** — 10 statements alternating positive/negative on a 5-point Likert scale; computed score 0–100. SUS > 68 is "above average". Quick, robust, comparable across systems.

### Variants

- **Cafe studies (guerilla usability testing)** — short tests in a public place for quick, cheap feedback; good for walk-up-and-use apps, first use, onboarding. Challenges: recruiting, noisy/uncomfortable locations.
- **Wizard-of-Oz** — participant interacts with a prototype whose behaviour is enacted by a human, believing it's the computer; used for systems that don't yet exist or where reaction to "the real thing" matters (usually ML systems). Challenge: too realistic → users think it's ready to use.

### How many participants & dogfooding

- **~5 users** gives best returns (same diminishing returns as HE/CW); better to **iterate** (test → fix → test again) than over-recruit; multiple target groups → **3–5 per group**.
- **Dogfooding** — asking your **own employees** to use your own product. Used when prospective-user studies are hard (commercial confidentiality, need critical mass, hard to incentivise/get honest feedback). Drawbacks: employees unrepresentative, bias toward internal norms, reluctance to give negative feedback to colleagues.

### Remote vs in-person

- **In-person** — richer non-verbal signal; lab environment unrealistic; easier moderation.
- **Remote moderated** — diverse participants, own setup (ecological validity), harder to read body language.
- **Remote unmoderated** (UserTesting.com style) — scale, lower cost; less depth; sample bias toward platform users.

**Choosing an evaluation method** depends on: time, cost, detail, risk; type of understanding required; context (consumer/enterprise/service); user activities (sequential vs overlapping, complex vs simple, layman vs expert) — mirrors the user research method choices.

## 13 · Accessibility and inclusive design

### Why design accessibly?

- **Legal:** Equality Act 2010 (UK), ADA (US), EU Web Accessibility Directive — public-sector sites must meet WCAG 2.1 AA.
- **Ethical:** ~15% of the population has a disability per WHO, plus many temporary/situational impairments.
- **Practical:** accessibility benefits everyone — captions for crowded environments, keyboard nav for power users, plain language for non-native speakers.

### WCAG principles — POUR

1. **Perceivable** — info presented so all users can perceive it (alt text, captions, contrast).
2. **Operable** — UI usable by all (keyboard, time limits, no seizure-inducing flashes).
3. **Understandable** — text and behaviour predictable.
4. **Robust** — works with assistive tech (semantic HTML, ARIA used correctly).

**Conformance levels:** **A** (essential), **AA** (legal baseline often), **AAA** (gold standard, sometimes impractical).

### Keyboard accessibility

Every interactive element reachable by **Tab**, logical tab order matches visual order; visible focus indicator (`:focus-visible`); skip-to-content link at top; no "keyboard traps" — can always escape.

### Screen readers

- Semantic HTML (`<button>`, `<nav>`, `<h1–6>`, `<main>`) carries meaning the screen reader announces.
- Use **ARIA only where HTML can't express the role** — first rule of ARIA: don't use it if a native element exists.
- **Alt text** for non-decorative images; empty `alt=""` for decorative ones; **live regions** (`aria-live`) for dynamic updates.
- Test with VoiceOver (macOS), NVDA/JAWS (Windows), TalkBack (Android).

### Visual & cognitive accessibility

- **Contrast:** WCAG AA ≥ 4.5:1 for body text, ≥ 3:1 for large text. **Colour-blindness:** don't convey info by colour alone — pair with shape/text.
- **Resizable text** to 200% without breaking layout; **avoid auto-playing motion** (`prefers-reduced-motion`).
- **Cognitive:** plain language, consistent/predictable navigation, avoid time pressure where possible, provide multiple representations (text + diagram + video).

### Inclusive design vs accessibility

- **Accessibility** focuses on disability. **Inclusive design** is broader — design for the widest range of human variability (disability, age, language, culture, expertise, device, environment, network). Microsoft's *Inclusive Design Toolkit*: "Solve for one, extend to many."
- **Curb-cut effect** — designing for the edge often improves the centre (curb cuts for wheelchairs also help parents with strollers, delivery couriers, travellers with luggage).

### Universal design — 7 principles (Mace, 1997)

1. Equitable use. 2. Flexibility in use. 3. Simple and intuitive. 4. Perceptible information. 5. Tolerance for error. 6. Low physical effort. 7. Size and space for approach and use.

## Common pitfalls

- **"User likes it" ≠ "user can use it"** — preference and performance dissociate; don't substitute satisfaction surveys for task-based testing.
- **Recruiting friends/colleagues** for research or testing biases findings toward people who think like the design team.
- **Heuristic evaluation finds violations but not necessarily impact** — pair with usability testing to confirm real-world severity.
- **Skipping low-fi prototyping** "to save time" causes costly late-stage changes once fundamental flaws surface (10× cost-escalation rule).
- **Testing too late** — "design it then test it" is far costlier than building evaluation into the iterative cycle from the start.
- **Hi-fi prototypes mistaken for finished products** by stakeholders ("it looks done, ship it") and by users (entering real data into a non-functional prototype).
- **A single heuristic evaluator** finds only ~35% of problems — aim for 3–5 (diminishing returns beyond ~5).
- **Cognitive walkthrough done by the system's own designer** — cognitive bias; "unlearning" the design is essential for credible analysts.
- **Closure (Gestalt) can mislead** — a chart with a gap is perceptually "completed" into a smooth curve even when real data was jagged; don't rely on viewers spotting missing data.
- **ARIA misuse** — slapping ARIA roles onto inaccessible JS widgets usually breaks more than it fixes; prefer semantic HTML.
- **Confusing "what users would do" with "what the team thinks is sensible"** — both CW and HE require modelling the *user's* mental model, not the designer's.
- **Personas/journey maps treated as "the whole user"** — the "what you see is all there is" bias; people are diverse (devices, assistive tech, expectations).

## Exam strategy

- **For "evaluate this design"** — pick **3 Nielsen heuristics**, cite specific UI elements that violate them, and give a severity rating (0–4) with justification (frequency × persistence × impact).
- **For "design a study"** — follow the structure: research question → participants → tasks → environment → pilot → recruit → run → analyse, plus ethics (informed consent, withdrawal, confidentiality).
- **Quote the UCD cycle** verbatim if asked: understand context → specify requirements → produce design solutions → evaluate against requirements → iterate.
- **Quote the cognitive walkthrough's four questions verbatim** and apply them per-step for an onboarding-flow question, rather than dumping heuristics.
- **For requirements questions**, use the Wiegers & Beatty hierarchy (business → user → functional requirements) and classify functional vs non-functional/quality requirements explicitly.
- **For "why is X usable/unusable"**, reach for Gestalt principles (similarity, proximity, enclosure, common fate, figure/ground, closure, good continuation) and memory/attention implications (chunking, recognition > recall, progressive disclosure).
- **For accessibility questions**, quote **POUR** and pair each issue with a concrete impairment and WCAG level; cite the curb-cut effect for "why inclusive design helps everyone".
- **For prototyping fidelity questions**, justify by *what you intend to evaluate* — state the fidelity, the artefact, the participants, and the metric you'll record.
