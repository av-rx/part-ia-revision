## 1 · What is a DBMS

### Terminology

| Term | Meaning |
|---|---|
| **Value** | character string / number / date / polygon etc. |
| **Field** | place to hold a value (attribute / column) |
| **Record** | sequence of fields (row / tuple) |
| **Schema** | spec of table/field names, types, consistency rules |
| **Key** | field(s) used to locate a record |
| **Index** | derived structure for fast lookup |
| **Query** | retrieve/lookup function |
| **Update** | modification of data, preserving consistency |
| **Transaction** | atomic change of a set of fields |

A DBMS provides a **narrow, standardised interface** over secondary storage, shared by concurrent applications — application writers are freed from low-level storage details. **Data independence** (changing physical layout without breaking queries) is the central design goal, though performance concerns and changing specs challenge it in practice.

### Variations of set-ups

- **Storage location:** primary (in-core), secondary, distributed.
- **In-core persistence:** ephemeral vs persistent (serialised to filesystem, or DBMS directly accesses secondary storage).
- **Data size:** Big Data (too big for primary store) vs in-core (fits entirely in memory).
- **Write pattern:** read-optimised (rarely changes), transaction-optimised (many concurrent updates), or append-only journal (ledger-style).
- **Consistency model:** ACID vs BASE. **Data arrangement:** relational, semi-structured documents, or graphs.

### Consistency concerns

- **Value range checks** — e.g. reject a weight of −15 kg.
- **Foreign key referential integrity** — reject a reference to a non-existent record.
- **Value atomicity** — don't store "two addresses" in one field.
- **Entity integrity** — every field must have a value.

### CRUD and management operations

**CRUD:** Create, Read, Update, Delete. **Management operations:** create/change schema, create a view (e.g. access control), physically reorganise/re-index, backups, statistics generation.

### Data models

| Model | Characteristics |
|---|---|
| **Relational** | Data in tables; SQL; optimised for high-throughput concurrent updates |
| **Document-oriented (aggregate-oriented)** | Semi-structured; optimised for read-heavy, few-update workloads |
| **Graph-oriented** | Mostly nodes/edges; strong path-query and graph-algorithm support |

In a **relational database**, each table has one row per record, each record has fields (attributes). The schema specifies field names, allowable formats/ranges, and which column(s) form the key. Column order is unimportant, often row order too.

### Distributed databases & CAP theorem

Reasons to distribute: **scalability** (dataset/workload too large for one machine), **fault tolerance** (survives failure of some machines), **lower latency** (data near widely distributed users). Downside: **consistency** has overhead, with a spectrum of relaxed consistency models (do all viewers see updates in the same order?) — the same problem arises within multi-core processors, not just distributed systems.

**CAP theorem** — pick at most two of:
- **Consistency** — all reads return up-to-date data.
- **Availability** — all clients can find *some* replica of the data.
- **Partition tolerance** — system continues operating despite arbitrary message loss/partial failure.

Impossible to guarantee all three under a network partition. Distributed systems instead offer **BASE** (Basically Available, Soft state, Eventual consistency) — once updates cease, the system eventually reaches a consistent state.

## 2 · Conceptual modelling with ER diagrams

ER modelling is **abstract and implementation-independent** — clarifies design before worrying about tables, and communicates the design visually.

### Core notation

- **Entities** — nouns (rectangles/squares).
- **Attributes** — properties (ovals); **key** attribute is underlined.
- **Relationships** — verbs connecting entities (diamonds), with a defined **scope** (only relevant attributes modelled).

### Cardinality

- **Many-to-many (M:N):** any instance of $S$ relates to zero or more of $T$, and vice versa.
- **Many-to-one / one-to-many:** e.g. each `Employee` belongs to exactly one `Department` (M:1 from Employee's side); one `Department` has many `Employees` (1:N from Department's side) — same relationship, two views.
- **One-to-one (1:1):** both entities relate to at most one of the other. Rare — usually suggests merging the entities. Note: 1:1 *cardinality* doesn't imply a true 1-to-1 *correspondence* (some instances may have zero matches).

Different notations exist (crow's foot, (min,max) pairs) — be consistent and label both ends of every relationship.

### Relationships with attributes

A relationship can carry an attribute — e.g. `PLAYS` between `Person` and `Movie` might have a `role` attribute. Each attribute occurs **once per relationship instance**, causing problems if an actor plays multiple roles in one movie (can't hold two `role` values).

### Multi-valued attributes

Avoid comma-separated lists or multi-valued attributes — violates **1NF** (atomic values). Instead pull repeating values into a separate entity/relation (e.g. a list of "roles" becomes a `Role` entity linked by a relationship).

### Ternary relationships

A relationship can involve **three** entities at once. Key question: is the third "entity" actually meaningful? A ternary relationship can sometimes be replaced by binary relationships, but risks losing information or creating an artificial entity purely to hold the connection (e.g. a `Casting` entity capturing Person–Movie–Role as two binary relationships).

### Attribute vs entity with new relationship

Depends on **scope**: if all movies have exactly one release date, `release_date` is a simple attribute of `Movie`; if a movie can have multiple release dates (different countries/formats), model `MovieRelease` as a separate entity with its own relationship to `Movie`.

### Weak entities

A **weak entity** depends on an owner entity for existence — e.g. `AlternativeTitle` only exists relative to a `Movie`. Drawn as a **double rectangle**.

- A **discriminator** distinguishes multiple weak-entity instances of the same owner (e.g. `alt_id`) — **not unique on its own**, **not a key**.
- To uniquely identify a weak entity instance, you need **both** the owner's key (`movie_id`) **and** the discriminator (`alt_id`).

### Entity hierarchy

Entities may have sub-entities ("is-a" hierarchies). Sub-entities **inherit** the parent's attributes (including keys) and relationships.

## 3 · The relational model and relational algebra

### Mathematical foundations

For sets $S$ and $T$:

- **Cartesian product:** $S \times T = \{(s,t) \mid s \in S, t \in T\}$.
- A **(binary) relation** is any set $R \subseteq S \times T$.
- An **n-ary relation** $R \subseteq S_1 \times \dots \times S_n = \{(s_1,\dots,s_n) \mid s_i \in S_i\}$.

A **database relation** associates a name $A_i$ (attribute) with each domain $S_i$, and uses *records* — sets of (attribute name, value) pairs. The **schema** of $R$ is $R(A_1{:}S_1, \dots, A_n{:}S_n)$.

A **query language** takes relation instances $R_1,\dots,R_k$ and produces $Q(R_1,\dots,R_k)$. It must be **high-level** (no storage management) and **declarative** (what, not how).

### Relational algebra operators

Closed: every operator takes relation(s) and produces a relation, so operators compose.

| Operator | Symbol | Meaning |
|---|---|---|
| Selection | $\sigma_p(R)$ | tuples of $R$ where predicate $p$ holds |
| Projection | $\pi_X(R)$ | restrict each tuple to attributes $X$ |
| Renaming | $\rho_M(R)$ | rename attributes via map $M$ |
| Union | $R \cup S$ | tuples in $R$ or $S$ (same schema) |
| Intersection | $R \cap S$ | tuples in both |
| Difference | $R - S$ | tuples in $R$ but not $S$ |
| Cartesian product | $R \times S$ | all pairings of tuples |
| Join | $R \bowtie_\theta S$ | $\sigma_\theta(R \times S)$ |
| Natural join | $R \bowtie S$ | equi-join on all shared attributes |
| Division | $R \div S$ | "for all" queries |

### Natural join in detail

Write $R(\boldsymbol{A}, \boldsymbol{B})$ to mean $R(\boldsymbol{A} \cup \boldsymbol{B})$ with $\boldsymbol{A} \cap \boldsymbol{B} = \emptyset$. Notation $u.[\boldsymbol{A}] = v.[\boldsymbol{A}]$ abbreviates $u.A_1 = v.A_1 \land \dots \land u.A_n = v.A_n$.

Given $R(\boldsymbol{A}, \boldsymbol{B})$ and $S(\boldsymbol{B}, \boldsymbol{C})$, the **natural join** $R \bowtie S$ over $\boldsymbol{A}, \boldsymbol{B}, \boldsymbol{C}$ is:

$$R \bowtie S \equiv \{t \mid \exists u \in R, v \in S,\ u.[\boldsymbol{B}] = v.[\boldsymbol{B}] \land t = u.[\boldsymbol{A}] \cup u.[\boldsymbol{B}] \cup v.[\boldsymbol{C}]\}$$

Expressed in core relational algebra:

$$R \bowtie S = \pi_{\boldsymbol{A},\boldsymbol{B},\boldsymbol{C}}\left(\sigma_{\boldsymbol{B}=\boldsymbol{B}'}\left(R \times \rho_{\boldsymbol{B} \mapsto \boldsymbol{B}'}(S)\right)\right)$$

In SQL this is `NATURAL JOIN` (vs `CROSS JOIN`), or more commonly an explicit `JOIN ... ON` with the matching condition spelled out.

### Joins and complexity

Naive **nested-loop join** of $R(A,B)$ and $S(B,C)$:

```
for each (a, b) in R {
    for each (b', c) in S {
        if b = b' then create (a, b, c) ...
    }
}
```

Worst case $O(|R| \times |S|)$ — but each $R$ row may match only a few $S$ rows (e.g. one, if $B$ is a foreign key into $S$). An **index** on $S.B$ replaces the inner scan with a lookup, giving $O(|R| \log |S|)$ instead of $O(|R| \times |S|)$. Trade-off: **indexes speed up reads but slow down writes** (must be maintained on every update).

### Multisets and NULL

- SQL queries naturally produce **multisets**, not sets — hence `DISTINCT`. Duplicates matter for aggregates (`MIN`, `MAX`, `AVG`, `COUNT`), typically with `GROUP BY`.
- **`NULL` is a placeholder, not a value** — not `""`, not a member of any domain/type. Forces **three-valued logic** (true/false/unknown). Interpretations are ambiguous ("value unknown", "no value applies", "value hidden", etc.). `NULL` is not equal to anything — **not even another `NULL`**.
- **Selecting on `NULL`:** use `IS NULL` / `IS NOT NULL` — `foo IS NULL` is always true or false, never unknown.
- **`GROUP BY` and `NULL`:** despite `NULL = NULL` being unknown, `GROUP BY` puts all `NULL`s into one group:

```sql
SELECT note, count(*) AS total
FROM credits
WHERE note IS NULL GROUP BY note;
-- note total
-- NULL 4892
```

This *looks* like `NULL = NULL` for grouping — a known SQL wart, inconsistent with the definition above.

## 4 · From ER model to relational schema

### Why not use one big table?

A single denormalised table suffers **redundancy anomalies**:

- **Insertion anomaly:** hard to tell if a new record is consistent with existing ones; may want to insert a person without knowing if they're a director, or a movie without its director.
- **Deletion anomaly:** deleting all of a director's films loses all info about that director.
- **Update anomaly:** fixing a misspelled director's name in one film but not others leaves data inconsistent.
- **Performance:** a conceptually simple update may touch many rows, potentially locking the whole table.

Breaking a large table into smaller tables (one per ER entity, one per ER relationship) avoids these anomalies, at the cost of needing **joins** to recombine information.

### Keys — formal definition

For $R(\boldsymbol{X})$ with $\boldsymbol{Z} \subseteq \boldsymbol{X}$:

- $\boldsymbol{Z}$ is a **superkey** if for any two records $u,v$: $u.[\boldsymbol{Z}] = v.[\boldsymbol{Z}] \implies u.[\boldsymbol{X}] = v.[\boldsymbol{X}]$.
- $\boldsymbol{Z}$ is a **key** if it's a superkey and **no proper subset** is also a superkey (minimal).
- $R(\underline{\boldsymbol{Z}}, \boldsymbol{Y})$ indicates $\boldsymbol{Z}$ is a key for $R(\boldsymbol{Z} \cup \boldsymbol{Y})$.

### Foreign keys and referential integrity

Given $R(\underline{\boldsymbol{Z}}, \boldsymbol{Y})$ and $S(\boldsymbol{W})$ with $\boldsymbol{Z} \subseteq \boldsymbol{W}$: $\boldsymbol{Z}$ is a **foreign key in $S$ for $R$** if $\pi_{\boldsymbol{Z}}(S) \subseteq \pi_{\boldsymbol{Z}}(R)$ in every instance — every $\boldsymbol{Z}$-value in $S$ also appears as a key in $R$. A database has **referential integrity** when all such constraints hold.

### SQL schema/key examples

```sql
CREATE TABLE genres (
    genre_id integer NOT NULL,
    genre TEXT NOT NULL,
    PRIMARY KEY (genre_id));

-- All-key table implementing an M:N relationship:
CREATE TABLE has_genre (
    movie_id varchar(16) NOT NULL REFERENCES movies (movie_id),
    genre_id integer NOT NULL REFERENCES genres (genre_id),
    PRIMARY KEY (movie_id, genre_id));
```

### Mapping ER constructs to tables

| ER construct | Relational implementation |
|---|---|
| Strong entity | one table; PK = entity's key |
| Weak entity | one table; PK = (owner's PK, discriminator) |
| 1:1 relationship | merge into one participating table; FK on either side |
| 1:N relationship | FK on the "N" side, referencing the "1" side's PK |
| M:N relationship | new all-key table containing both PKs, each a FK |
| Multi-valued attribute | new table: (owner PK, value) |

### Squashing multiple relationships into one table

Two relations $R(\underline{X,Z}, U)$ and $Q(\underline{X,Z}, V)$ (both keyed on $(X,Z)$) can be combined into $RQ(\underline{X,Z,\text{type}}, U, V)$ using a tag column `type` $\in \{\boldsymbol{r}, \boldsymbol{q}\}$: an $R$-record $(x,z,u)$ becomes $(x,z,\boldsymbol{r},u,\text{NULL})$; a $Q$-record $(x,z,v)$ becomes $(x,z,\boldsymbol{q},\text{NULL},v)$. The `type` value tells you which of $U,V$ is meaningful (the other is `NULL`).

### Implementing weak entities & hierarchies

For a weak entity owned by $S(\underline{Z}, W)$ with discriminator $\text{DISC}$:

- **Two-table:** $R(\underline{Z,\text{DISC}}, U)$ and $T(\underline{Z,\text{DISC}}, Y)$, both with $\pi_Z(\cdot) \subseteq \pi_Z(S)$.
- **Concise:** a single $R(\underline{Z,\text{DISC}}, U, Y)$ — e.g. `Has_Alternative` (alternative movie titles).

**Entity hierarchies (3-table approach):** for parent $S(\underline{Z}, W)$ with two sub-entity types, each sub-entity gets its own table $T(\underline{Z}, Y)$ / $U(\underline{Z}, V)$ with $\pi_Z(\cdot) \subseteq \pi_Z(S)$, sharing the parent's key. (Could combine into one table with a type tag, as above, but "less clean".)

## 5 · Normalisation, functional dependencies, and redundancy

### What redundancy means and why it matters

Data is **redundant** if it could be deleted and *reconstructed* from data remaining in the database.

- **Problematic** — data held in multiple places can come to disagree (inconsistency); a correct transaction must lock and update many copies.
- **Sometimes good** — if updates are rare, multiple copies increase read bandwidth and speed up lookups.

A **normal form schema** has little/no redundancy: every piece of data is either part of the key, or **semantically depends on** the key. If data doesn't directly depend on the key, split it into a separate table — repeating until **closure** (no further splits needed). "Splitting off" is division-like; reversible by a **join** (multiplication-like). This is the same closure/fixed-point idea as iterating a transform to termination (e.g. repeated rewriting until no rewrite applies).

### Functional dependencies and normal forms

A **functional dependency (FD)** $X \to Y$: any two tuples agreeing on $X$ must agree on $Y$. Keys are the special case where $X$ determines *every* attribute.

**Armstrong's axioms** derive all implied FDs:

- **Reflexivity:** if $Y \subseteq X$, then $X \to Y$.
- **Augmentation:** if $X \to Y$, then $XZ \to YZ$ for any $Z$.
- **Transitivity:** if $X \to Y$ and $Y \to Z$, then $X \to Z$.

The **closure** $X^+$ is the set of attributes functionally determined by $X$, computed by repeatedly applying Armstrong's axioms until no more attributes can be added (another fixed-point computation). $X$ is a (super)key iff $X^+$ is the full attribute set.

| Form | Requirement |
|---|---|
| **1NF** | All attribute values atomic; no repeating groups/multi-valued attributes |
| **2NF** | 1NF, and every non-prime attribute **fully** depends on the *whole* primary key (no partial dependency on part of a composite key) |
| **3NF** | 2NF, and no non-prime attribute **transitively** depends on the key (no non-prime → non-prime dependency) |
| **BCNF** | Every non-trivial FD $X \to Y$ has $X$ as a superkey |

BCNF is stricter than 3NF: decomposing into BCNF can require a split 3NF wouldn't, and this split can leave some FDs checkable only via a join (not **dependency-preserving**), even though it remains **lossless** (information-preserving).

### Redundancy / consistency / throughput trade-off

- **Low redundancy** → good update throughput (a transaction locks few items).
- **High redundancy** → good query times (fewer files/blocks accessed — data needed together is stored together).
- Redundancy can cause **stored inconsistency** if updates aren't applied to every copy; **unlocked reads** can also appear inconsistent (some copies read pre-update, others post-update).
- **Precomputing common queries** speeds response but introduces redundancy — useful for read-intensive applications.

### OLAP vs OLTP

| | OLAP | OLTP |
|---|---|---|
| Pattern | Write-once / journal / ledger-style | Rich mix of queries and updates to live data |
| Optimised for | Read-heavy analytics, often denormalised | Many concurrent small read/write transactions |

A read-oriented (OLAP) database makes sense when data is rarely updated but read often and reads can tolerate mild staleness — periodically extracting a read-optimised snapshot from a live OLTP system is common. Redundancy speeds reads at the cost of slowing/complicating writes.

## 6 · SQL essentials and further SQL

### Anatomy of a query

```sql
SELECT a.name, AVG(b.score) AS avg_score
FROM Author a
JOIN Book b ON a.id = b.author_id
WHERE b.year > 2000
GROUP BY a.name
HAVING COUNT(b.id) >= 3
ORDER BY avg_score DESC
LIMIT 10;
```

- `WHERE` filters **rows** before grouping; `HAVING` filters **groups** after `GROUP BY`.
- `JOIN` defaults to `INNER JOIN`; `LEFT`/`RIGHT`/`FULL OUTER JOIN` keep unmatched rows from one/both sides (padded with `NULL`).
- **Aggregates** `COUNT, SUM, AVG, MIN, MAX` — all except `COUNT(*)` ignore `NULL`s. `COUNT(*)` counts every row including `NULL`s; `COUNT(col)` counts non-`NULL` `col` values only.
- **Set operations:** `UNION`, `INTERSECT`, `EXCEPT` on two compatible queries; `UNION` removes duplicates, `UNION ALL` keeps them.
- **Subqueries:** scalar (one value), `IN` (membership), `EXISTS` (correlated existence), general correlated subqueries.
- **CTEs:** `WITH t AS (...) SELECT ... FROM t`; standard SQL also allows **recursive** CTEs (`WITH RECURSIVE`).

### Function composition and relation composition

Function composition: $f(g(x)) = y \implies (f \circ g)(x) = y$ (OCaml: `let compose (f, g) = fun x -> f (g x)`).

**Relation composition** generalises this: for $R \subseteq S \times T$ and $Q \subseteq T \times U$,

$$Q \circ R \equiv \{(s,u) \mid \exists t \in T.\ (s,t) \in R \land (t,u) \in Q\}$$

A function is a relation where each input maps to a unique output, so function composition is a special case — **joins generalise function composition** to relations. Concretely, $Q \circ R$ is the join $R \bowtie_{2=1} Q$ (joining $R$'s 2nd column to $Q$'s 1st).

### Directed graphs, paths, and transitive closure

A **directed graph** $G = (V, A)$ has vertices $V$, arcs $A \subseteq V \times V$. For $R \subseteq S \times S$, define **iterated composition**: $R^1 \triangleq R$, $R^{n+1} \triangleq R \circ R^n$. If $(u,v) \in A^k$, there is a path of length $k$ from $u$ to $v$.

**Shortest path:** distance from $s_0$ to itself is 0; if $(s_0,s_1) \in R$, distance 1; in general, the distance to $s'$ is the least $n$ with $(s_0,s') \in R^n$.

**Transitive closure** $R^+$ is the smallest transitive relation with $R \subseteq R^+$:

$$R^+ = \bigcup_{n \in \{1,2,\dots\}} R^n = R \cup R^2 \cup \dots \cup R^k$$

for some finite $k$ (data-dependent, not known ahead of time). **Plain relational algebra and non-recursive SQL cannot compute transitive closure** — recursion is required.

### Recursive SQL

```sql
WITH RECURSIVE countUp AS (
    SELECT 1 AS n
    UNION ALL
    SELECT n + 1 FROM countUp WHERE n < 3
)
SELECT * FROM countUp;
```

### Worked example: Bacon numbers

Classic transitive-closure problem: find, for every actor, the shortest co-appearance chain length to Kevin Bacon (`person_id = 'nm0000102'`).

View of co-actor pairs:

```sql
CREATE VIEW coactors AS
    SELECT DISTINCT p1.person_id AS pid1, p2.person_id AS pid2
    FROM plays_role AS p1
    JOIN plays_role AS p2 ON p2.movie_id = p1.movie_id;
```

Bacon number 1 — direct co-stars of Bacon:

```sql
CREATE VIEW bacon_number_1 AS
    SELECT DISTINCT pid2 AS pid, 1 AS bacon_number
    FROM coactors
    WHERE pid1 = 'nm0000102' AND pid1 <> pid2;
```

Bacon number $n+1$ follows the same pattern — co-actors of bacon-number-$n$ people, excluding Bacon and anyone already assigned a smaller bacon number (each successive view adds one more `NOT IN (SELECT pid FROM bacon_number_k)` clause). The full result unions `bacon_number_1` through `bacon_number_9`, then counts actors per distance with `GROUP BY bacon_number`.

**The recursive equivalent** of the whole hand-unrolled chain:

```sql
WITH RECURSIVE bacon(n,pid) AS
    (SELECT 0 AS n, pid2 AS pid
        FROM coactors
        WHERE pid1="nm0000102" AND pid1=pid2
    UNION
    SELECT n+1 AS n, c.pid2 AS pid
        FROM bacon
        JOIN coactors AS c ON c.pid1 = pid
        WHERE NOT (c.pid2 IN (SELECT pid FROM bacon))
        AND n < 20
    )
    SELECT n, COUNT(*)
        FROM (SELECT min(n) AS n, pid FROM bacon GROUP BY pid)
        GROUP BY n;
```

The hand-unrolled `bacon_number_N` views are exactly what the recursive CTE computes automatically — recursion terminates when no new `pid`s are added (a fixed point/closure), bounded by `n < 20` as a safety limit.

## 7 · Transactions, ACID, throughput, and consistency

### Transaction processing

A **transaction** is a series of queries/updates that *externally appear* as a single atomic operation.

- **Internal transactions:** values are read, possibly more conditionally read, and values changed based on what was read — all within the same database.
- **External "transactions" don't really exist:** side effects outside the DBMS (e.g. sending an SMS) can't be made atomic by the DBMS — designers must think about "undoing" such effects if the transaction aborts. Some systems let the application abort before commit.

### Transaction client flow & ACID

A transaction is bracketed by `START`/`BEGIN` and `COMMIT`, containing any number of queries/updates:

- The client may **abort** any time — the DBMS undoes all updates.
- In **optimistic** systems, an update or commit may be rejected, forcing a restart.
- DBMSs support many transactions running **concurrently**.

**ACID properties:**

- **Atomicity** — all changes happen as one operation, or none do. *E.g.* a funds transfer both debits and credits, or does neither.
- **Consistency** — a transaction on a consistent DB leaves it consistent. *E.g.* total money across accounts is conserved.
- **Isolation** — intermediate states invisible to others; concurrent transactions appear serialised. *E.g.* a concurrent transaction sees funds in one account or the other, never both/neither.
- **Durability** — once committed, changes persist across system failure. *E.g.* account changes are never silently reversed.

**ACID vs BASE:** many NoSQL systems weaken ACID to **BASE** — **B**asically **A**vailable, **S**oft state, **E**ventual consistency.

### Locking, 2PL, and recovery

Implementing ACID requires **locks** (mutual exclusion). A resource locked exclusively must be unlocked after use; other transactions wanting it wait, delaying completion.

- Locks are **acquired/released by transactions** (vendor-specific protocol); range from **coarse-grained** (whole DB) to **fine-grained** (single value).
- Locking large or frequently-used data → fewer concurrent updates → **throughput degrades**.

**Two-phase locking (2PL):**

- **Growing phase:** acquire locks but never release.
- **Shrinking phase:** release locks but never acquire.
- **Strict 2PL** holds all locks until commit/abort — guarantees **recoverability** and **serializability**; what most real systems implement.

**Deadlock:** transactions wait on each other's locks in a cycle. Detected via a **wait-for graph** (cycle = deadlock), or prevented via timeouts/lock ordering.

**Crash recovery** uses a **write-ahead log (WAL)**: log every change before applying, supporting **undo** (roll back uncommitted) and **redo** (replay committed changes lost from memory), with periodic **checkpoints** to bound recovery time.

> **2PL ≠ two-phase commit.** 2PL is *concurrency control* (lock phases within one transaction); two-phase commit is a *distributed atomicity* protocol for committing across multiple nodes.

## 8 · Semi-structured / document databases

### What "semi-structured" means

E.g. a textbook: chapters with names and (sub)sections, figures with their own numbering, cross-references between sections — doesn't fit a rigid relational schema, yet has organisational structure. Manually indexing every word would be too much work and not useful.

**Approaches:**
- **Two parts:** keep the document in native form, separately store *indexable features* in relational tables.
- **Store once** (possibly **shredded**): keep the document largely in native form (XML/JSON), with tools that navigate it directly using non-SQL queries, returning **best-effort** answers (schema violations may be frequent). Documents can also be **"unshredded"** back to original form. Human curators or automatic tools (keyword analysis, LLM/NLP) can remove noise, index, and classify when adding structure.

### BASE revisited — three orthogonal axes

1. Tables vs documents.
2. Distributed vs centralised.
3. ACID vs BASE.

Document databases are typically designed to be **easy to distribute** and **don't support full ACID** — hence BASE:

- **B**asically **A**vailable — availability over consistency; a change at one node propagates to all others (eventually).
- **S**oft **S**tate — stored values may change without application intervention (eventual-consistency updates, partition resolution).
- **E**ventual **C**onsistency — all readers eventually see the same state.

### Key/value stores

Values are arbitrary blobs, **opaque** to the store. Many implementations are distributed, spreading data as **shards** (e.g. by hash of key) for redundancy and load balancing. Since the DBMS doesn't interpret values, it doesn't mind encrypted values. Implementations range across the ACID–BASE spectrum.

### Serialisation: JSON and XML

**Serialising** (marshalling/pickling) converts a data structure into bytes for transfer/storage.

- **JSON** was designed for serialising data; **XML** for serialising *and* marking up human-readable documents (different parts located/processed differently).
- Both (and CSV) widely used for transferring data between databases/apps; NoSQL systems often use JSON/XML as the primary on-disk form.

Same data in XML and JSON:

```xml
<PERSON name="Greaves"><DOB month="May" year="1902"/></PERSON>
```

```json
"person": {"name": "Greaves", "dob": {"month": "May", "year": "1902"}}
```

Both are fundamentally **tree-structured text with named nodes** — broadly similar abstract syntaxes (XML: elements with attributes + children or leaf text; JSON: objects/arrays/leaves/null).

### XML structure and schema spectra

**Structure spectrum:** (1) all data in one large element (unstructured) → (2) **semi-structured** (some elements free text, others single atomic values, as in a relational DB) → (3) every atomic value in its own element (unrealistic).

**Schema rigorousness spectrum:** (1) named schema dictates element names/nesting/attributes → (2) relaxed (e.g. element ordering unimportant) → (3) extra elements/attributes beyond schema permitted → (4) no schema at all.

### Document-oriented (aggregate-oriented) databases

Store data as semi-structured **objects** (aggregates). Distinguish from raw key/value stores: a key/value store *could* hold unstructured documents, but application-level structure inside the blobs **can't be exploited by the DBMS**. Querying a remote DB incurs **round-trip time**; document databases typically store **denormalised** data — fields not semantically related to the key are stored together under it — so **one or two fetches** retrieve everything an operation needs, avoiding further round trips.

### Document query languages

Query types: the **unstructured text** itself (e.g. "how many words?"), **tags/structure** (e.g. "find the `eye-colour` attribute of each `Vizier` under the second `Chapter`"), or application-specific compositions. A path-expression abstract syntax (cf. XPath) navigates the tree via operations like `SelectRoot`, `SelectAttribute`, `SelectElement` (by predicate), `NextElement` (move by $n$), `SelectData` (raw text ranges), `Concatenate` (aggregation). If a query spans more than one tree, something equivalent to a **join** is also needed.

### NoSQL, denormalisation, and schema-free

"NoSQL" databases are typically **horizontally scalable** (add machines rather than upgrade). A common pattern: **precompute and store the same data under several different keys/nestings**, so likely access patterns are served by a single fetch — but the **replication factor multiplies** (fault-tolerance replication compounds with denormalisation replication).

Many fields are strings/numbers that represent something more specific (units, or a foreign key into another table). Making such types **explicit (branded)** rather than raw strings/ints prevents nonsensical operations (e.g. adding a `person_id` to a `movie_id`).

"No schema" really means "not stored as part of the database, not checked on update" — **not** that no schema exists. There's always *some* implicit schema (whiteboard, document, or someone's head); the DBMS just doesn't enforce it, so new developers must learn it elsewhere.

## 9 · Graph-oriented databases

### Basic model

A graph database typically stores **one graph**:

- **Nodes** have a type, unique label, properties.
- **Edges** are directed between two nodes, with a type plus optional label and properties.

Nodes/edges of the same type can be **collated** into equivalent rDBMS tables if needed.

### Why not just use relational tables for graphs?

A naive encoding (one table for nodes, one for edges with artificial `EID`) is **inefficient**:

- Finding a node's neighbours requires scanning **all edges**.
- Undirected searches need **both** endpoint columns checked (endpoints interchangeable).
- Multi-hop queries require many self-joins.
- Typically need **two inverted indexes** on the edges relation (one per endpoint) for tractable lookups.

A slightly better layout uses one table per node type plus an all-key edges table (no `EID`) — but rDBMS representations remain poor for enormous many-to-many relations; OLAP-style analysis would instead use a **denormalised** representation. (A binary relation where all edges go from one node type to another is **bipartite**.)

### Neo4j / Cypher basics

Nodes/edges written `<name>:<type>` with key/value properties. **All edges have a direction as stored**, but queries can treat them as undirected.

**Graph normalisation caution:** don't use a role name as the *arc name* itself:

```cypher
(nm0000084)-["Su Li-zhen":PLAYS_ROLE]->(tt0212712)
```

Arc *names* must be unique, so the same role name reused across actors/movies (e.g. a remake) would clash. Instead store the role as a **property** of a generically-named edge:

```cypher
(nm0000084)-[:PLAYS_ROLE {role: 'Su Li-zhen'}]->(tt0212712)
```

### General observations on graph DBs vs rDBMS

- An arc **type** models an ER **binary (or unary) relation**.
- **Pattern matching on paths** is natively supported.
- **Transitive closure is free and built in** — no recursive CTE gymnastics.
- Many other graph algorithms supported out of the box.

Neo4j notes: edges created without identifiers are **not idempotent** (re-running creates duplicates); edges directed as stored but traversable as **undirected**; queries can be packaged as **reusable functions with formal parameters**; has had **serious security vulnerabilities** historically (as can rDBMS); regex matching on property values **violates value atomicity**, but predicate-based matching is allowed.

### Pattern-matching query examples

**Friends-of-friends:**

```cypher
MATCH (john {name: "John"})-[:FRIEND]->()-[:FRIEND]->(fof)
RETURN john.name, fof.name
```

**Co-actors** — "people who acted in the same movie", two equivalent forms:

```cypher
MATCH (p1:Person)-[:ACTED_IN]-> (m:Movie),
      (p2:Person)-[:ACTED_IN]-> (m:Movie)
WHERE p1.person_id <> p2.person_id
RETURN p1.name AS name1, p2.name AS name2, count(*) AS total
ORDER BY total desc, name1, name2
LIMIT 10;
```

```cypher
MATCH (p1:Person)-[:ACTED_IN*2]- (p2:Person)
WHERE p1.person_id <> p2.person_id
```

The second form uses Cypher's variable-length path syntax (`*2` = exactly 2 hops) — "transitive closure is free" in action.

### Graph algorithms, metrics, and uses

Graph DBMSs need efficient support for:

- **Community:** edge/node ratio, diameter, clustering, tree count.
- **Centrality:** how important is each node/link to overall structure.
- **Similarity:** how alike are two or more nodes?
- **Prediction:** how likely is a new arc between two nodes?
- **Path finding:** "best" path between two nodes.

Optimised for **Big Data** (graphs too large for primary memory) data-science queries — e.g. social network visualisation, friend recommendation. **In-core databases** can use raw pointers for referential links; **Big-data implementations** stream edges past processing elements rather than holding the whole graph in memory.

### Worked example: Bacon numbers in Cypher

The transitive-closure-heavy Bacon computation (~9 hand-unrolled views, or a recursive CTE, in SQL) becomes one query with `allshortestpaths`:

```cypher
MATCH paths=allshortestpaths(
    (m:Person {name : "Kevin Bacon"} )-[:ACTED_IN*]-(n:Person))
WHERE n.person_id <> m.person_id
RETURN length(paths)/2 AS bacon_number,
       COUNT(distinct n.person_id) AS total
ORDER BY bacon_number;
```

(Path length is divided by 2 because each "hop" between actors via a shared movie is two edges in the `ACTED_IN` graph — actor→movie→actor.)

## Common pitfalls

- **`NULL` is not a value** — `x = NULL` is always *unknown*, never true; always use `IS NULL` / `IS NOT NULL`.
- **`NULL` is not equal to another `NULL`** — yet `GROUP BY` puts all `NULL`s into a single group, which can look inconsistent with that definition.
- **`COUNT(*)` vs `COUNT(col)`** — `COUNT(*)` counts all rows including `NULL`s; `COUNT(col)` ignores rows where `col IS NULL`.
- **`HAVING` vs `WHERE`** — `HAVING` runs after `GROUP BY` on aggregated groups; can't reference an unaggregated raw column in `HAVING` unless it's in `GROUP BY`.
- **Weak entity keys** — a discriminator alone is *not* a key; need (owner key, discriminator) together.
- **BCNF vs 3NF** — BCNF can force a decomposition 3NF wouldn't require, possibly not dependency-preserving (some FDs checkable only via a join), though still lossless.
- **Two-phase locking ≠ two-phase commit** — 2PL is concurrency control; two-phase commit is distributed-atomicity across nodes.
- **Indexes are a trade-off** — speed up reads ($O(S) \to O(\log S)$) but slow down every write that maintains them.
- **Redundancy is a dial, not a binary** — low redundancy favours write/update throughput (fewer locks); high redundancy favours read/query throughput (fewer joins/files touched).
- **Transitive closure needs recursion** — plain relational algebra/non-recursive SQL provably cannot compute it; use `WITH RECURSIVE` or a graph DB's native path operators.
- **CAP is about partitions specifically** — you only choose between C and A *when a partition occurs*; normally a system can be both.
- **Document DB denormalisation multiplies replication** — storing the same aggregate under multiple keys for different access patterns compounds with fault-tolerance replication.

## Exam strategy

- **ER diagrams:** draw them; underline keys; label cardinalities on *both* ends of every relationship; mark weak entities with double rectangles and identify the discriminator explicitly.
- **Relational algebra:** know the closure property (every operator's output is a relation); be ready to express a natural join as $\pi(\sigma(R \times \rho(S)))$ from first principles.
- **SQL:** indent and align — readability wins partial credit. For recursive queries, structure your CTE as (base case) `UNION` (recursive step with termination condition).
- **Normalisation:** write out *every* FD explicitly, compute attribute closures using Armstrong's axioms, and check each normal form's condition systematically (1NF → 2NF → 3NF → BCNF) rather than guessing.
- **ACID:** name all four properties with a one-line concrete example each (reuse the funds-transfer example).
- **Transactions/locking:** mention 2PL's growing/shrinking phases explicitly and distinguish from two-phase commit; mention WAL for recovery.
- **Document vs graph vs relational:** argue *trade-offs* (denormalisation, ACID vs BASE, join cost vs index-free adjacency) rather than just stating "graph DBs are good for graphs".
- **Transitive closure / Bacon numbers:** a favourite — practice writing both the iterative (`UNION` of numbered views) and recursive CTE forms, and the Cypher `allshortestpaths` equivalent.
